# M4 解析与审查流程设计规格

## 1. 目标与范围

M4 将 M3 已有的制度、版本、关系、账号与权限能力，扩展为可运行的文件解析和审查发起流程。交付范围包括：

1. 正式制度版本的 `.docx`、文字 PDF 上传和持久化。
2. 临时待审文件的上传、解析和隔离存储，且不进入制度库。
3. 文件解析状态、结构化条款保存、条款展示和重新解析。
4. 从制度库或临时文件选择待审来源，并指定一个或多个条款。
5. 选择一个、多个或全部审查维度。
6. 在选择制度冲突维度时，从有关联关系的制度中召回候选条款，并由用户确认最终候选。
7. 保存审查输入快照，生成不可编辑的自动编号，并独立保留重复审查记录。

M4 不执行四维智能判断，不生成审查问题或报告内容。四维模型调用、规则判断、证据状态和问题处理属于 M5。M4 不增加用户可见的任务名称、风险等级、置信度或持久化任务状态。

## 2. 测试数据基线

以仓库中的 `制度审查测试数据集/` 为解析规则和演示数据基线。

- 将四份待审 Markdown 制度分别生成内容一致的 `.docx` 和文字 PDF，共八个固定测试文件。
- 生成文件保存到 `制度审查测试数据集/生成文件/`。
- DOCX 与 PDF 使用相同的章节、条款和正文内容，以便断言两种格式解析结果一致。
- 生成的 DOCX 与 PDF 只作为测试夹具和演示数据，不作为最终单位制度模板。
- DOCX 和 PDF 生成后必须分别完成结构检查、文字提取检查和页面渲染检查。

## 3. 文件存储与生命周期

### 3.1 正式制度文件

正式文件绑定到具体制度版本。数据库保存原文件名、受控相对路径、扩展名、MIME 类型、文件大小、SHA-256、解析状态、失败原因和解析时间；文件正文保存在 Docker 持久化文件卷。

上传新制度或新版本时，后端先写入文件，再创建版本记录并进入“待解析”。上传权限继续使用 M3 的 `PERM-001`。不支持的格式在落库前拒绝。

### 3.2 临时待审文件

临时文件拥有独立实体和条款集合，记录上传人、原文件名、受控路径、文件元数据和解析状态。它不创建制度或制度版本，也不出现在制度列表、制度检索或关系维护中。

临时文件在 M4 中持续保存，以支持历史审查记录回看。删除周期尚未确认，因此 M4 不实现自动清理策略。

### 3.3 安全路径

服务端生成存储文件名，不信任上传文件名作为磁盘路径。所有路径必须解析到配置的文件根目录内。真实上传文件、数据库文件、环境变量和密钥不进入 Git。

## 4. 解析架构

### 4.1 组件边界

- `DocumentParser`：统一解析接口，输入文件路径和原始文件名，输出有序段落。
- `DocxParser`：使用 `python-docx` 读取正文段落，跳过表格。
- `PdfTextParser`：使用 PyMuPDF 读取可选择的文字层；没有有效文字时返回“疑似扫描件，不支持 OCR”。
- `ClauseSegmenter`：把有序段落转换为章节和条款，不依赖具体文件格式。
- `ParseService`：管理状态转换、文件校验、解析执行、条款原子替换和错误记录。

这些组件不依赖 FastAPI 路由，可直接进行单元测试。格式解析与条款切分分离，以便获得真实单位制度后只替换切分规则。

### 4.2 第一版结构识别规则

识别顺序如下：

1. `第X章` 识别为章，支持中文数字和阿拉伯数字。
2. `第X节` 识别为节，挂在最近的章下。
3. `第X条` 识别为条，作为可选审查条款的主要单位。
4. 以 `（X）`、`(X)`、`X.`、`X、` 开始的段落，在条款内部识别为款或项，但不拆成独立审查条款。
5. 其他非空段落附加到最近的条款；在首条之前出现的正文保存为前置段落。
6. Markdown 测试源中的 `#`、`##` 和引用说明不写入生成制度文件。

每条制度条款保存：系统编号、原编号、标题、正文、层级、标题路径、段落起止序号、原始顺序、所属制度版本或临时文件。

第一版不解析表格、不做 OCR、不检查字体字号等视觉格式、不使用页码、不提供条款合并拆分或人工改层级功能。

### 4.3 状态与重新解析

状态仅为“待解析、解析中、解析成功、解析失败”。解析开始时更新为“解析中”；全部条款写入成功后更新为“解析成功”；任何异常回滚本次条款写入并记录可读失败原因。

重新解析复用原文件。新结果先在事务内完成，再替换旧条款，避免失败时丢失上一次成功结果。前端展示当前状态、失败原因和重新解析入口。

## 5. 候选条款召回

### 5.1 检索范围

只有待审来源为正式制度且选择了“制度冲突”维度时执行候选召回。候选制度范围来自该制度当前可见的上位、下位、关联、引用和被引用关系，排除自身、已业务删除制度和解析未成功版本。

临时文件没有正式制度关系。M4 对临时文件选择制度冲突维度时，前端提示用户先选择用于比较的制度；用户选择的制度构成检索范围，不自动建立制度关系。

### 5.2 混合召回

采用两个可独立替换的检索器：

- 关键词检索：使用 `jieba` 分词，并对制度名称、条款编号和正文计算词项匹配分数。
- 向量检索：M4 默认使用确定性的本地哈希向量器，保证无 API Key 时可运行和可重复测试；向量接口与模型标识独立，M5 可替换为智谱 Embedding Provider。

PostgreSQL 环境将向量保存为 `pgvector`；SQLite 自动化测试通过相同服务接口在 Python 内计算距离，不把测试数据库行为伪装成 PostgreSQL 方言能力。

两路结果使用倒数排名融合（RRF）合并。召回数量、RRF 常数和最低展示分数是部署配置，不作为业务规则写死在页面。响应展示来源制度、关系类型、条款位置、原文和召回依据，不向用户展示模型置信度。

用户最后勾选的候选条款 ID 才进入审查输入快照；未选择的候选不会保存为冲突审查输入。

## 6. 审查发起与记录

### 6.1 输入流程

1. 用户选择制度库来源或临时上传来源。
2. 来源解析成功后，用户勾选一个或多个条款。
3. 用户选择语义分歧、规则匹配、制度冲突、一致性中的一个、多个或全部维度。
4. 包含制度冲突时召回候选，用户选择最终候选条款。
5. 后端校验条款确实属于待审来源，候选条款属于本次允许的检索范围。
6. 后端创建审查记录和不可变输入快照。

### 6.2 记录结构

审查记录保存：自动编号、来源类型、正式制度或临时文件标识、显示名称、待审条款快照、所选维度、候选条款快照、创建人、创建时间和完成时间。

编号格式为 `待审制度名称-YYYYMMDD-当日序号`。同日序号由数据库事务生成，用户不能修改。对同一制度、临时文件或条款重复发起审查时，每次生成独立记录。

M4 创建记录后，页面显示“审查输入已保存，四维分析将在 M5 执行”，然后可返回审查记录列表。该反馈是当前请求结果，不作为任务状态字段保存。

### 6.3 数据快照

记录同时保存条款 ID 和发起时的原文、原编号、位置、来源制度名称与版本。后续制度重新解析或上传新版本时，历史审查输入仍保持可追溯。

## 7. API 与前端

新增 API 能力：

- 正式制度版本文件上传与重新解析。
- 临时文件上传、状态查询、条款读取与重新解析。
- 制度或临时文件条款列表。
- 冲突候选召回。
- 审查记录创建、列表和详情读取。

前端修改范围：

- 制度新增、版本和详情页面接入真实文件上传与解析状态。
- 制度详情展示真实条款和重新解析按钮。
- 发起审查页面移除 M4 演示占位，接入两类真实来源、真实条款、真实候选和记录创建。
- 审查记录页面改读后端数据，无任务状态列或状态筛选。
- M5 报告页面保留现有演示入口，但 M4 新建记录不伪造智能问题。

## 8. 错误处理

- `.doc`、图片和非 PDF/DOCX 文件：返回明确的不支持格式错误。
- PDF 无有效文字：返回疑似扫描件且不支持 OCR 的错误。
- DOCX 损坏或加密、PDF 损坏：解析失败并保存可读原因。
- 文件落盘失败：不创建可见版本或临时文件记录。
- 重复解析：串行化同一来源的解析操作，避免并发覆盖。
- 候选范围为空：返回空集合，前端提示维护制度关系或选择比较制度。
- 用户提交不属于来源的条款或越界候选：拒绝请求，不创建审查记录。
- 自动编号并发冲突：在事务中重试生成，不暴露重复编号。

## 9. 测试与验收

后端测试至少覆盖：

1. 四份 DOCX 与对应 PDF 解析出的章、条编号和正文一致。
2. 综合样例保留第九条到第十一条的原编号和顺序，不自动伪造第十条。
3. `.doc`、图片、扫描型空文本 PDF 被拒绝并给出准确原因。
4. 解析状态转换、失败原因和重新解析后的原子替换。
5. 临时文件不出现在制度库。
6. 候选制度范围遵循正式关系；临时文件使用用户选择的比较制度。
7. 关键词和向量结果经 RRF 去重融合。
8. 只保存用户选中的待审条款、维度和候选条款。
9. 同一来源重复审查生成不同编号和独立快照。
10. 上传与解析接口的角色和权限边界。

前端验证至少覆盖：

1. 正式制度上传、解析状态、条款展示和重新解析。
2. 临时文件上传后不进入制度列表。
3. 单条、多条、单维、多维和全部维度选择。
4. 制度冲突候选选择与无候选空状态。
5. 新建记录进入真实历史列表且没有任务状态筛选。

最终验证包括后端完整测试、Alembic 升级、PostgreSQL/pgvector 集成测试、前端类型检查、生产构建和浏览器端到端检查。

## 10. 设计决策与后续边界

- 本地确定性向量器是 M4 的可运行默认实现，不代表最终模型选择。
- 智谱 Embedding 接入、DeepSeek 或智谱对话模型、四维提示词和结构化问题输出在 M5 实现。
- 真实单位制度到位后，使用同一解析器接口增加或调整条款切分策略，不改变上传、条款、候选和审查记录 API。
- 临时文件自动清理、性能阈值、安全策略和生产备份继续遵循现有开放项，不在 M4 中擅自固化。
