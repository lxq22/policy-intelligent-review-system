## 2. 已实现能力

### 登录与权限

- 自有用户名、密码登录，无公开注册。
- 密码使用 Argon2 哈希保存。
- 登录后由后端设置 HttpOnly Cookie，数据库只保存随机会话凭据的哈希。
- 停用账号无法登录，账号停用和密码重置会清除已有会话。
- 审查人员和系统管理员在前后端均进行角色隔离。
- 上传制度、删除制度、关系管理三项权限同时由界面和 API 校验。

密码复杂度、会话期限、登录失败锁定等参数没有擅自固化，继续等待非功能需求确认。

### 组织、分类和单位

- 部门和制度分类的查看、新增、修改、删除接口。
- 一级单位和二级单位及其隶属关系。
- 页面提供部门、分类、单位隶属的新增、修改和删除操作。
- 防止二级单位缺少所属一级单位，以及带有二级单位的一级单位被直接删除或降级。
- 基础数据写操作受关系管理权限控制。

### 制度和版本

- 按名称、部门、制度层级和生效状态检索。
- 制度新增和信息编辑。
- 制度状态只接受“生效中”和“已失效”。
- 新版本保存、旧版本保留和替代说明。
- 审查人员业务删除、管理员恢复。
- 管理员不具备制度编辑和报告内容接口。

字段仍采用宽松数据库模型，没有擅自增加尚未确认的必填、唯一、长度或日期联动规则。

### 制度关系

- 同部门制度按当前数据实时生成双向关联。
- 一级单位制度与所属二级单位制度按当前隶属实时生成上下位关系。
- 手工关系持久化后，目标制度自动显示对应反向关系。
- 疑似引用只保存为待确认建议，确认后才建立正式关系。
- 制度详情页可确认已匹配建议、标记待匹配建议，并删除人工关系。
- 重复提交相同可见关系不会产生重复记录。
- 正式关系区分系统自动、人工确认和手工添加来源。

因为自动关系按当前数据实时计算，所以没有固化“部门或隶属变更后如何处理旧自动关系”的未确认规则。

### 操作历史

- 只记录制度新增、删除和恢复。
- 管理员可以查看和删除操作历史。
- 删除操作历史时支持一并删除该制度关联的历史审查记录。
- 管理员可修改审查人员姓名和所属部门；删除曾创建关系的人员不会删除业务关系。

## 3. API

主要接口分组：

- `/api/v1/auth`
- `/api/v1/regulations`
- `/api/v1/master-data`
- `/api/v1/admin`

启动 API 后，可通过 `/docs` 查看 FastAPI 自动生成的 OpenAPI 文档。

## 4. 验证结果

- 后端测试：10 项全部通过，SQLite 测试启用外键约束。
- 前端 TypeScript 检查和 Vite 生产构建：通过。当前网络无法访问 npm 注册表，因此最终复检直接使用已安装的本地构建程序，没有重新下载依赖。
- Alembic：显式迁移可完成升级、模型一致性检查和降级；PostgreSQL 方言 SQL 成功生成。
- Compose 文件：成功解析，包含 `db`、`api`、`frontend` 三个服务。
- 浏览器联调：真实登录、制度列表、基础数据修改、制度详情、关系建议确认与人工关系删除、管理员人员资料修改和角色路由隔离通过；页面控制台无错误。
- 联调中发现的退出登录 204 响应问题已修复，并增加回归测试。

Docker Desktop 4.84.0、Docker Engine 29.6.2 和 Compose v5.3.1 已安装并验证。2026-08-03 尝试实际启动组合环境时，主机与 Docker 均无法连接 `auth.docker.io:443`，镜像拉取发生 TLS 超时。因此 PostgreSQL 容器实测仍待网络/VPN或代理恢复，不能以 SQLite 验证替代；当前浏览器联调使用隔离 SQLite 数据库。
